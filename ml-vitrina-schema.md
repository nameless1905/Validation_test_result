# Схема витрины данных под ML-пайплайн (на основе схемы вашей ЛИС)

## Важное открытие по схеме — читайте перед остальным

Ваша ЛИС — это **система коммерческой диагностической лаборатории** (розничная сеть), а не больничная ЛИС с полной клинической картиной. Видно по характерным таблицам: `loyaltydata`, `discountevent`, `promocode`, `competitor`, `informationsource` (маркетинг), интеграция с ЕПГУ (`sendtoepgu`), `petdata` (ветеринарные анализы). Это принципиально меняет один из ключевых элементов архитектуры, которую мы обсуждали раньше.

**Критический пробел: в схеме нет поля клинического диагноза для обычных заказов.** Единственное поле `diagnosis` во всей базе находится в таблице `histologyreferrals` (направление на гистологию) — и относится только к гистологическим исследованиям, не к CBC/биохимии. Таблица `orders` содержит `insurancepolicy` (номер полиса), а не диагноз — представление `dirtyorders` зачем-то делает `insurancepolicy AS diagnosis`, что выглядит как историческая ошибка/переименование поля разработчиками, а не источник реального диагноза. **Уточните это у вашей ИТ-команды отдельно** — не полагайтесь на это поле как источник диагноза без проверки.

**Что это значит для проекта:** ключевое конкурентное преимущество LLM-подхода (мы разбирали это на примере статьи Mindray) — сопоставление отклонений с клиническим диагнозом/фазой лечения. У вас в базе **этого контекста физически нет**, потому что коммерческая лаборатория в общем случае не знает диагноз пациента — только то, что назначил направивший врач (`orders.doctor`), и то не всегда. Это не блокирует проект, но меняет его экономику:

- Прирост качества от LLM для вас будет **меньше**, чем в статье Mindray (75%→93%), потому что там ключевой драйвер прироста — именно сопоставление с диагнозом.
- LLM всё ещё даст пользу за счёт истории результатов пациента (дельта-чек с клиническим рассуждением, а не жёсткими порогами), морфологических флагов и общих медицинских знаний — но без диагноза модель не сможет объяснить "цитопения ожидаема на фоне химиотерапии", потому что не будет знать, что пациент вообще проходит химиотерапию.
- Если у лаборатории есть партнёрские больницы/клиники, откуда приходят направления с указанием диагноза (даже в свободном текстовом поле бланка-направления, не оцифрованном в БД) — стоит проверить, есть ли этот текст где-то на бумаге/скане направления и можно ли его завести в структурированном виде отдельным полем. Это единственный реалистичный путь вернуть эту ценность.

## Карта соответствия: поля вашей ЛИС → поля целевой схемы `case`

| Поле целевой схемы | Источник в вашей ЛИС | Комментарий |
|---|---|---|
| `case_id` | Генерируется в витрине (не берём `measurecontext.id` напрямую, чтобы не палить внутренний PK) | — |
| `analyzer.model` | `analyser.name` (через `method.analyser_id` → `analyser.id`) | Название анализатора текстом, не структурированная модель — нормализуйте на этапе ETL |
| `analyzer.reagent_lot` | `reagentlots.lotnumber` (через `method.reagent_id` → `reagents.id` → `reagentlots.reagent_id`) | Хэшировать при выгрузке за периметр |
| `analyzer.run_id` | `automate_event.id` / связка через `automate_event.samplenumber` + `workplacecode` | Прямой связи `automate_event` → `measurecontext` в схеме нет — придётся связывать по номеру пробы + временному окну |
| `patient_context.patient_pseudo_id` | Хэш от `patients.id` (canonical) — НЕ от `orders.id`, т.к. один пациент = много заказов | Обязательно `patients.id`, не ФИО из `orders`/`sample` (там ФИО дублируется как снапшот) |
| `patient_context.age_years` | Расчёт от `patients.birthdate` (или `orders.birthdate`/`sample.subjectbirthdate`, если различаются — см. риски ниже) | — |
| `patient_context.sex` | `patients.gender` (int-код, нужен словарь расшифровки) | В `orders` и `sample` есть дублирующие поля `sex`/`subjectgender` — могут расходиться, см. ниже |
| `patient_context.clinical_diagnosis_codes/text` | **Отсутствует в схеме** (см. раздел выше) | Оставлять пустым/`unknown`, пока не найден альтернативный источник |
| `patient_context.treatment_phase` | **Отсутствует** | То же |
| `patient_context.ward_type` | Частично — `orders.origin`, `orders.createdondepartment_id` → `department.category` | `department.category` — тип отделения, может дать что-то вроде "розничная точка"/"стационар-партнёр", если такие типы вообще заведены |
| `current_result.collected_at` | `sample.samplingtimestamp` | Не `orderline.completiontimestamp` — это момент забора, а не готовности результата |
| `current_result.indices.*` | `measurecontext` (одна строка = один показатель): `numericvalue`/`result`, `measuringunit_id` → `measuringunits.name`, `normalminvalue`/`normalmaxvalue`, флаг из `resultrefcharstatus` + `lessflag`/`moreflag` | `measureparameter_id` → `measureparameter.code`/`shortname` даёт код показателя (WBC/PLT и т.п.) — критично для унификации кодов между разными assay |
| `current_result.instrument_flags` | Частично из `autocomment` (текстовые интерпретационные комментарии, привязанные к `method_id` + диапазону значения) | Это не флаги анализатора в чистом виде (типа IG_present/blast_suspect от гематологического анализатора), а сконфигурированные в ЛИС правила комментариев — см. раздел "Что нужно доуточнить" |
| `current_result.scattergram_abnormal` | **Не найдено в схеме** | Возможно, приходит от анализатора как часть `automate_event.description` (текстовое поле) — нужно смотреть реальные данные |
| `current_result.morphology_findings` | Не структурировано — вероятно, в `measurecontext.comment`/`refcharcomment` как свободный текст, если морфология вообще заводится этой ЛИС отдельным assay | Уточните, есть ли отдельный `assay` для морфологии/мазка и как он связан с CBC-заказом |
| `historical_results` | Предыдущие `measurecontext`, связанные через `patient_pseudo_id`, отфильтрованные по `measureparameter_id` и `collected_at < текущей` | Строится агрегацией в витрине, не хранится как есть в ЛИС |
| `delta_check` | Не хранится в ЛИС как отдельное значение — считается в витрине | `method.maxdeviatecoeff` — это порог допустимого отклонения, уже настроенный в ЛИС для дельта-чека методом; используйте его как референс при расчёте |
| `rule_based_engine_output.verdict` | `orderline.state` (машина состояний) + `orderline.techvalidated_at` (момент тех. валидации) | Нужна расшифровка кодов `state` — не видна в дампе схемы (это entries в коде приложения/enum, не в БД) |
| `rule_based_engine_output.triggered_rules` | `method.validationscript`, `autocomment` (сработавшие правила по диапазону) | `validationscript` — код скрипта, не структурированный список правил; для полноценного лога срабатывания правил, скорее всего, нужен отдельный источник (логи приложения ЛИС), в дампе БД такого лога нет |

## Обнаруженные полезные технические поля, которых не было в нашей исходной схеме `case`

- **`method.autovalidation`** (boolean) — прямой флаг: включена ли автовалидация для конкретного метода/показателя. Это готовый признак "находится ли данный показатель вообще под автовалидацией по вашей текущей настройке" — обязательно вытащить в витрину, он размечает объём применимости проекта по каждому измеряемому параметру.
- **`method.maxdeviatecoeff`** — уже настроенный в ЛИС коэффициент допустимого отклонения (по сути, порог дельта-чека) на уровне метода. Ценно и для аудита текущего rule-engine (мы это обсуждали ранее), и как baseline-сигнал для модели.
- **`orderline.alert`/`alertmessage`** — булев признак и текст алерта на уровне строки заказа — ещё один источник сигналов текущей rule-логики, который стоит включить в `rule_based_engine_output`.
- **`orderline.quarantined`** — отдельный статус "карантин" (возможно, приостановка выдачи по другой причине, не связанной с автовалидацией — например, при повторном заборе) — стоит учитывать отдельно от verdict, чтобы не путать с решением о клинической валидации.
- **`qualitycontrol`** — таблица контроля качества (уровень, лот, среднее/СКО, результат по анализатору) — не про конкретного пациента, но критична для отдельного мониторинга дрейфа анализатора, который мы обсуждали в контексте `reagent_lot`.

## Предлагаемая архитектура витрины (३ слоя)

### Слой 1 — ETL/staging (из продовой ЛИС, псевдонимизация здесь)

Отдельная read-only реплика или scheduled-выгрузка (не прямые запросы в прод на каждый инференс). Здесь происходит:
- Замена `patients.id` на `patient_pseudo_id` (хэш с солью, соль — отдельно в vault).
- Удаление прямых идентификаторов (`firstname`, `lastname`, `middlename`, `phone`, `email`, `passportdata_id` и всё, что тянется через `orders`/`sample`/`patients`).
- Разрешение расхождений между `orders.sex`/`sample.subjectgender`/`patients.gender` — берём `patients.gender` как канонический источник, но логируем случаи расхождения отдельно (это может быть сигналом ошибки идентификации пробы — полезно и для проекта, и для общего качества данных ЛИС).

### Слой 2 — витрина фактов и измерений (ML-ready)

**Таблица фактов `fact_cbc_result`** (одна строка = один результат анализа, уже развёрнутый по параметрам в JSON-колонку `indices`, как в нашей схеме `case`):

```sql
CREATE TABLE mart.fact_cbc_result (
    case_id             uuid PRIMARY KEY,
    order_id            uuid NOT NULL,          -- ссылка на источник для аудита (внутри защищённого контура)
    orderline_id         uuid NOT NULL,
    sample_id           uuid NOT NULL,
    patient_pseudo_id    text NOT NULL,
    collected_at         timestamp NOT NULL,
    analyzer_model       text,
    analyzer_run_id      text,
    reagent_lot_hash     text,
    age_years            integer,
    sex                  text,
    ward_type            text,
    indices              jsonb NOT NULL,         -- {"WBC": {...}, "PLT": {...}, ...}
    instrument_comments  jsonb,                  -- из autocomment
    rule_engine_verdict  text,                   -- из orderline.state/alert
    rule_engine_flags    jsonb,
    created_at           timestamp DEFAULT now()
);
```

**Витрина измерений (справочники)** — тонкие таблицы для join, обновляются редко:
- `dim_measureparameter` (код показателя, единица измерения, каноническое имя WBC/PLT/... — нормализованное, не как в исходной `measureparameter.name`, где могут быть кириллические варианты написания).
- `dim_analyzer` (analyser.id → нормализованная модель).
- `dim_method_thresholds` (method_id, measureparameter_id, autovalidation, maxdeviatecoeff, minvalue/maxvalue) — снапшот настроек метода на момент результата (важно версионировать, т.к. пороги меняются со временем, а исторический результат должен трактоваться по порогам, действовавшим на момент его получения).

### Слой 3 — предрасчитанная история и дельта

**Таблица `fact_patient_history`** — для каждого `case_id` заранее посчитанные:
```sql
CREATE TABLE mart.fact_patient_history (
    case_id              uuid REFERENCES mart.fact_cbc_result(case_id),
    historical_results   jsonb,   -- последние N результатов по тому же measureparameter
    delta_check          jsonb    -- {"WBC_delta_pct": ..., "PLT_delta_pct": ...}
);
```

Считается batch-джобом при появлении нового результата (join `fact_cbc_result` самого на себя по `patient_pseudo_id` + `measureparameter_id`, отбор последних N по дате до текущего `collected_at`), а не на лету при каждом инференсе — это то, что мы обсуждали как "структурированный retrieval" в контексте RAG.

## Что нужно доуточнить у вашей ИТ-команды/администратора ЛИС до начала ETL

1. **Расшифровка кодов `orderline.state`** и `measurecontext.resultrefcharstatus` — в дампе структуры БД это просто `integer`, расшифровка значений (какое число значит "норма", "выше нормы", "критично" и т.д.) обычно живёт в коде приложения или в таблице типа `enumrefcharliteral`/`enumerationliteralcode` — стоит выгрузить содержимое этих справочных таблиц, а не только структуру.
2. **Реальное содержимое `autocomment`** — насколько эти комментарии соответствуют "флагам анализатора" (типа IG_present/blast_suspect), или это просто текстовые интерпретации типа "консультация врача рекомендована" — нужно посмотреть примеры данных.
3. **Есть ли вообще в CBC-заказах морфологическое исследование** (пересмотр мазка) как отдельный `assay`, и если да — как он связан с исходным заказом ОАК (через `sample_id`? через отдельный `orderline` в том же `order`?).
4. **Природа поля `orders.insurancepolicy`** — подтвердить, что это действительно номер страхового полиса, а не диагноз (несмотря на алиас в `dirtyorders`), и есть ли где-то ещё в системе (не в этом дампе — может, в другом модуле/интеграции) текст направления от врача, который мог бы дать хоть какой-то клинический контекст.
5. **Связь `automate_event` с `measurecontext`** — прямого FK в схеме нет; нужно подтвердить логику связывания (по номеру пробы + временному окну, как в `actual_automate_event`) для восстановления `run_id`.

Это именно те вопросы, ответы на которые определят, насколько богатым получится ваш `case`-объект — без них часть полей (`instrument_flags`, `morphology_findings`, `scattergram_abnormal`) в реальности будет либо пустой, либо потребует данных, которых просто нет в этой ЛИС.
